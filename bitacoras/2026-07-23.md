## Qué entendí bien

- Para copiar un repositorio a mi cuenta de GitHub es necesario seleccionar la opción `fork`. Mientras que, si se cuenta con los permisos, se puede clonar a un repositorio local con `git clone <url-del-repositorio>`. Git entonces descarga el directorio de trabajo en la ruta desde donde se ejecutó el comando. Por defecto, esta nueva carpeta tendrá el nombre del repositorio en línea, aunque también es posible darle el nombre que se desee con `git clone <url-del-repositorio> <nuevo-nombre>`. Para conocer la URL del repositorio, se debe acceder al repositorio de origen y seleccionar la opción "<> Code" $\to$ "HTTPS"
- Cuando un repositorio local está conectado a un repositorio remoto, Git distingue los cambios que se han dado en cada repositorio mediante el uso de ramas: para llevar el registro de los cambios en el repositorio local utiliza las ramas que ya hemos estado trabajando `nombre-de-la-rama`, mientras que los cambios realizados en el repositorio remoto se monitorean mediante las ramas de seguimiento remoto denotadas por `origin/nombre-de-la-rama`. Así, los cambios dados en el repositorio local no afectan al repositorio remoto ni viceversa pues se encuentran en ramas diferentes; por tanto, llevar los cambios de un repositorio a otro se resume en ejectura un `git merge`
- Para eliminar ramas locales es necesario ejecutar `git branch -d <rama>`, mientras que para eliminar ramas de seguimiento remoto en el repositorio local, además de necesitarse que las ramas correspondientes en el repositorio remoto hayan sido eliminadas, hace falta ejecutar `git fetch -p` para eliminar las ramas de seguimiento remoto guardadas aún en el repositorio local
- Los cambios que se hayan dado en el repositorio remoto, pero no en el repositorio local se pueden conocer mediante `git fetch`. Esto no modifica el estado del repositorio local, sino que solo actualiza las ramas de seguimiento remoto. Estas ramas luego pueden ser operadas mediante los comandos `git log` o `git diff` para conocer cuáles fueron esos cambios que se dieron en el repositorio remoto y, si el dueño del repositorio local así lo considera, luego pueden ser aceptados en el repositorio local con un `git merge` en la rama local correspondientes a las ramas de seguimiento remoto. Estas dos operaciones son las que lleva a cabo `git pull` con un solo comando
  - Nota. Si el repositorio remoto cuenta con una rama que el repositorio local no, se puede ejecutar `git switch -c <nombre-de-la-rama> origin/<nombre-de-la-rama>` para que esa rama también se aloje en el repositorio local
- Los cambios en el repositorio local se pueden llevar al repositorio remoto con el comando `git push`. Esto puede hacerse de dos formas:
  1. Por medio de la fusión de la rama de integración y la _feature branch_ en el repositorio local para después llevar los cambios del repositorio local al repositorio remoto con `git push`
  2. Mediante un _pull request_. Existen diferentes maneras de hacerlo, pero quizá la más cómoda sea mediante la interfaz de GitHub. Allí, una vez se cuenten con las ramas que desean fusionarse, te puedes redirigir a la pestaña de Pull request y comenzar uno nuevo
  - Nota. Si los cambios fueron dados en una rama que el repositorio remoto aún no conoce, la primera vez que se ejecute el comando `git push` se debe introducir en qué rama se desea que se guarden los cambios y la rama de la que provienen los cambios con `git push -u origin <nombre-de-la-rama>`
- Bajo el supuesto de que en un equipo de más de un colaborador, con cada uno teniendo su _feature branch_ donde trabajar sus cambios para luego llevar esos cambios a la rama `main`, si, durante el tiempo en el que desarrollabas una rama dentro de tu repositorio local, uno o más colaboradores realizaron cambios en la rama `main` del repositorio remoto, entonces corres el riesgo de que tu rama termine tan desactualizada respecto a `origin/main` que, al momento de abrir tu propio pull request, aparezcan conflictos que hubieran sido más fácil resolver en pequeños pedazos a lo largo del camino. Cuando esto ocurra, puedes tomar una de las siguientes decisiones. En cualquiera de los dos casos, el punto es que nunca te atraces con los cambios que se hayan dado en el repositorio remoto. Aunque yo prefiero la primera opción
  1. Hacer un `git pull` dentro de la rama `main` para fusionarla con `origin/main`, luego muévete a la _feature branch_ y ejecuta `git merge main` para llevar estos cambios a tu _feature branch_
  2. Estando en tu _feature branch_, hacer un `git fetch` y luego un `git merge origin/main`
